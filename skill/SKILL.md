# dsh-plugin-compat-check

回答一个问题：**我这一版 DSH 上，我已经装了的插件有哪些兼容性证据与限制**。API源码发现有真实位置才给`file:line`；loader或声明事实用实际包身份、状态和依据说明，不编造源码行。

判定内核只有一处实现（`lib/verdict.mjs`，经 `bin/compat-check.mjs` 暴露），插件 / 脚本 / 本 skill 三个入口共用它。只有相同目标、版本、规则与采样证据才应得到相同结果。默认 CLI 用静态证据，当前宿主插件使用进程内观测，两者结论和基线模式可以不同；先核对证据，不把差异直接当缺陷。

## 先看能不能直接调工具

如果**当前会话已经注册了 `compat_check` 工具**（插件半边提供的对话入口，跑的是同一个内核），优先用它；没有就按下面的命令跑 CLI。两者结论同源，不要为了"多一点信息"去绕别的路。

## 怎么跑

CLI 只随仓库提供，npm 插件包没有 CLI bin。定位仓库检出，先在其根目录执行 `npm ci --ignore-scripts`；仓库必须同时有 `bin/compat-check.mjs`、`lib/`、`rules/`。先定位它，再跑：

```bash
# 1) 找到内核（仓库检出，不是已安装的 npm 插件目录）
ls <repo>/bin/compat-check.mjs

# 2) 体检「已装插件」。--nm 接受 profile 目录，也接受 node_modules 目录
node <repo>/bin/compat-check.mjs --nm ~/.dsh/profiles/<profile> --probe <probe-report.json> --dsh-version <版本>

# 机器可读 / 只要一行结论
node <repo>/bin/compat-check.mjs --nm ~/.dsh/profiles/<profile> --quiet
node <repo>/bin/compat-check.mjs --nm ~/.dsh/profiles/<profile> --json

# 一次性检查（CI、临时排查）：别在用户的 DSH_HOME 里留下基线文件
node <repo>/bin/compat-check.mjs --nm ~/.dsh/profiles/<profile> --no-baseline
```

完整的参数表以 `node bin/compat-check.mjs --help` 为准（**跑一遍再引用**，别凭记忆写旗标）。
`--help` 与 `--version` 都不需要 `--nm`，也不碰任何状态：

| 旗标 | 作用 |
|---|---|
| `--nm <dir>` | 必需。要体检的 `node_modules` 目录，或一个 profile 目录（会自动补 `node_modules`） |
| `--probe <json>` | 宿主运行时观测；身份、时间、完整性和调用点归属满足要求时，才可支持 certain 方法结论 |
| `--probe-boot` | **自己起一次宿主拿运行时面**（不必先有报告）。默认不开，会安装并执行目标插件；只在用户授权启动检查时使用，不保证每条结论都是 certain |
| `--probe-timeout <秒>` / `--probe-keep-dir <dir>` | `--probe-boot` 的等待上限（默认 40）/ 留一份探针报告到该目录（排查用） |
| `--dsh-version <v>` | 目标DSH版本，用于声明/peer范围判断；显式值优先 |
| `--json` / `--quiet` | 机器可读 / 只输出结论行 |
| `--no-baseline` | 不读写本机基线。**一次性检查用这个**，见下面的「副作用」 |
| `--rules` / `--catalog` | 覆盖规则表与官方 API 目录（默认在 `rules/`） |
| `--version` | 工具版本。**报结论时要带上它** —— 同一个插件在不同版本的规则表/提取器下结论会变，不带版本无法追溯 |

`--nm` 指哪里：`$DSH_HOME/profiles/<name>`（默认 `~/.dsh/profiles/<name>`）。用户说「我的插件」时，先弄清楚是哪个 profile，别默认 `desktop`。

运行时证据来源：

1. 优先复用当前 `compat_check` 的进程内观测，或用户已有的 `--probe <json>` 文件；现代文件需匹配 profile/DSH版本，默认超过24小时失效，旧文件明确标为未绑定。
2. 用户授权真实启动检查时，可显式使用 `--probe-boot`。它复制 profile、安装探针、启动自己的宿主并清理自己的现场；与 `--probe` 同时给时，文件优先。
3. 没有探针则按目录提供疑似线索；省略的服务是未采样，不能推断为不存在。CLI 也会尝试读取目标 node_modules 旁的 probe-report.json，转述前检查输出中的采样来源。

安装检查脚本 `--keep` 会返回本次唯一私有目录；CLI `--probe-keep-dir` 需显式给私有目录。报告与 boot.log 不再使用固定共享临时路径。`static.json` 来自 `node lib/extract.mjs <nm> <输出目录>`，不是每次安装检查都会自动产生的文件。

## 输出怎么读

```
插件数: 4    有运行时面: 是

采样说明: 旧格式探针未绑定 profile/DSH 版本；仅使用显式记录的服务，不推断缺项
工具版本: 0.1.2    证据覆盖有限: 4 个插件
结论: 可用 3    部分可用 1    不兼容 0    （其中 1 个「可用」是空洞的：它没有任何可检查的依赖）

部分可用  dsh-keep-awake@0.2.0
     功能失效 / 宿主方法缺失  settings.register  @ lib/index.js:466
       影响（推断，非实测）: 插件的设置页/设置项会消失
       依据: 运行时方法集没有此方法；源码存在未被方法能力检查保护的宿主调用
     客户端半边（命令行测不到，需界面验证）: locale, slots
     已过滤（判为噪音/有兜底）: jobs.onJobsChanged
     无证据可判（只出现名字，没有调用点）: timer
可用  @omdsh-dev/dsh-plugin-check@0.1.0
可用  dsh-pet@0.3.6
     客户端半边（命令行测不到，需界面验证）: commandUi, connection, locale, remote, remote.commands, slots
     已过滤（判为噪音/有兜底）: llm.listProviders, llm.listConfigurableProviders
可用  dsh-plugin-compat-check-probe@0.1.1   [空洞的结论：无可检查对象]
```

> ⚠️ 上面这段是**从真实运行里抄的**，而且**有一条测试盯着它**（`test/skill.test.mjs`：
> 把这段示例抽出来与真实输出逐行比对）。它曾经是编的 —— 里面写着
> `jobs.onJobsChanged @ lib/index.js:591` 是"降级"，而查源码 :590 是
> `if (jobs !== undefined && typeof jobs.onJobsChanged === 'function')`，
> **作者明明写了能力检测**，那是一条**假阳性**（已修）。
> 教训：**示例输出也必须从运行里抄**，否则 skill 会教 agent 去期待一个不存在的结论。

- **总结论**每插件一个：`可用` / `部分可用` / `不兼容` / `未知`。
- **API发现**通常包括位置；loader/声明事实可能没有源码行，不得编造位置。发现包括：严重度（`致命` / `功能失效` / `降级`）、类别（`宿主服务缺失` / `宿主方法缺失` / `无人提供的依赖` / `声明与实测不符` / `声明范围不兼容` / `宿主条目未激活`）、`服务.方法`、`@ 文件:行`。
- `影响` 与 `依据` 是给人验证用的：告诉用户**凭什么**这么判，而不是只给一个红叉。
- `[疑似]`：这一条没有运行时面支撑。转述时**必须**带上「疑似」，不能抹平成确定。
- `[空洞的结论：无可检查对象]`：这个插件没有任何可检查的依赖，"可用"是空的。别把它当成通过。
- `客户端半边（命令行测不到，需界面验证）`：列出来的服务**默认 CLI 不验证**，只能让用户去看界面上有没有该插件的元素。**不要替它下结论**。
- `已过滤（判为噪音/有兜底）`：报了但被判定为不构成问题（例如插件自己写了 `typeof x?.y === 'function'` 能力检测）。过滤与弃权**也是结论的一部分**，要如实转述，不要只报红叉。
- `无证据可判`：只出现名字、没有调用点。这是弃权，不是清白。
- **分清「事实」和「推断」**（`impactBasis` 字段）：
  - **影响**上方标了「**推断，非实测**」的 —— 那是**我们读代码得出的结论**，
    **不是**量出来的。工具只量到了「这个方法不在运行时里、调用点没有能力检测」，
    而「用户会失去什么功能」是**推断**。
    **转述时必须保留这个限定**，不要说成"确定会消失"。
    实测有过一条 certain 级假阳性：工具说「设置页会消失」，而作者把能力检测写在了
    一个辅助函数里、早就兜住了，还 log 了降级行为。
  - 只有显式`impactBasis=measured`且有对应观测，才按实测转述，例如明确记录的loader FAILED/PENDING。缺少字段或没有标注“推断”均不能当成实测；损坏报告应报工具错误。
- **转述结论时带上 `--version` 报出的工具版本**（`--json` 里是 `toolVersion`）。
  同一个插件在「规则表还没覆盖这个方法」和「已经覆盖」的两个版本下，
  结论可能从「影响面未知」变成「推断：可能影响设置页」—— 不带版本，用户无法判断该不该信。

## 退出码

| 码 | 含义 |
|---|---|
| `0` | 可用（未发现问题，仍需检查 coverage / vacuous） |
| `1` | 部分可用或未知；保留具体发现与证据限制 |
| `2` | 不兼容（有插件连基本依赖都不满足） |
| `3` | **无法判定**——工具/输入出了问题，**这不是插件的结论** |

`3` 必须与插件结论严格分开：`--nm` 指了不存在的目录、探针报告不是合法 JSON、渲染层抛异常，都退 `3`。看到 `3` 就说「这次没查成」，**绝不能说成"不兼容"或"部分可用"**（用的 flag 也对不上，这类混码见过）。

CI 里可以直接用：`0` 过，`1`/`2` 按你的策略处理，`3` 是**工具故障**，应该让流水线报错而不是静默放行。

## 判据：这个工具的三条硬规矩

**1. 确定性与去处分开。**
`certainty` 只有 `certain` 与 `suspected`；过滤、守卫、弃权是独立去处，不能当第三档确定性。声明能确定依赖关系，不单独证明方法不存在；目录不是运行时面。没有运行时面时方法级结论一律降为「疑似」。**「疑似」是诚实，不是缺陷**——把不确定的位置呈现得像确定一样，比不给位置更糟。

**2. 误报和漏报都要关注，漏报可能表现为「沉默」。**
判不准时一律**降级**，不升格成确定：假阳性会让用户去做不必要的处置（改配置、换版本），成本高且磨损信任。但反过来也要盯住——**假阴性不产出红字，它产出沉默**，而用户会把沉默当成「一切正常」。所以：
- 「没报」不等于「没问题」。要区分**查过了、没问题**和**没查成**。
- 先看 `有运行时面: 是/否`、`插件数: N`、退出码，再谈结论。
- `插件数: 0` + 退出码 `0` 是**最危险**的输出：它意味着一个插件都没检到，不是"全都好"。看到这个先回头确认 `--nm` 指对了没有。

**3. 「激活成功」不等于「功能可用」。**
插件可能通过`try/catch`或能力守卫处理缺失API，因此激活成功、日志干净既不能证明功能完备，也不能证明相应功能一定失效。具体业务行为须另行验收；`peerDependencies`/`engines.dsh`声明也不是功能证明，DSH官方peer版本闸门只检查semver范围，不验证每个API。

## 边界（不要越界承诺）

- **默认报告不验证客户端功能；可选开发工具能验证条目到货与浏览器错误。** 插件在浏览器里跑的部分（面板、标签页、设置卡片）需要人工在界面上确认；本工具只列出待确认项，不判定。
- **方法级判定使用 AST，但动态绑定与跨函数数据流仍有限**，可能有误报。拿不准时建议用户用脚本 `--keep` 保留探针与启动日志，并按需另运行源码提取输出 static.json。
- **默认静态检查的写入要主动说清**：默认会把这次结论写成本机基线
  （`$DSH_HOME/dsh-plugin-compat-check/baseline.<profile>.<path-hash>.<mode>.json`），好让下次对比出「相比上次变了什么」。
  一次性检查（CI、替别人看一眼）加 `--no-baseline`；`--dry-run` 是只算差分不写。除此之外它不装包、
  不改用户的 profile、不联网（显式 `--probe-boot` 和安装检查会安装并执行目标插件）。不要用它去"顺便修一下"。
- 报结论时**给出可核对的依据**。API源码发现引用真实`file:line`；没有源码位置的loader/声明事实说明包身份及观测或声明来源，不补造行号。


0.1.1：`root` 缺项是未采样，不能称为不存在；`coverage.status=limited` 与 `vacuous` 必须转述。现代探针绑定 profile/DSH/采样时间；旧报告明确标为未绑定。解析、读取、资源上限等诊断会限制覆盖，完整性不足不更新基线。当前统计见仓库 `docs/current-state.json`；npm 包是插件，CLI 从仓库使用并先运行 `npm ci --ignore-scripts`。显式安装检查会执行目标插件，临时 profile 不是不可信代码隔离沙箱。

官方 peer 范围冲突是 declared-incompatible：影响为推断，不能凭声明写成实际加载失败；当前实现沿用DSH0.2.0-rc.2的声明规则，将engines.dsh作建议处理；0.2.1-rc.1及rc.2宿主已优先按engines.dsh判断，存在声明误报/漏报风险，须说明该限制并核对宿主实际结果，不能称新版已全面适配。当前契约、施工记录和后续计划统一见仓库 docs/Plan.md，原始审计位于 docs/GPT审计及重构方案文档.md。本地版本以仓库文件为准；发布受理不等于公开可安装，公开版本以npm registry实时结果为准；本地修订不能视为已在公开包生效。
