# 静态提取的已知缺陷（实测记录）

这份文档记录**实测发现**的提取缺陷。它们不是"待打磨的细节"，而是会直接污染结论可信度的问题——而结论可信是这个工具唯一值钱的东西。

两批调查，都在这台机器上、DSH `0.2.0-rc.2`、样本是 `desktop` profile 的真实社区插件集：

| 批次 | 日期 | 怎么发现的 |
|---|---|---|
| 第一批（1–17） | 2026-10-10 | 移植到 Node 的过程中逐个撞上；后期靠**一条不变式**成批抓出（见下） |
| 第二批（18–28） | 2026-10-11 | 同一个工具体检**自己的依赖**时暴露；以及写夹具的自证过程 |

> **不变的规矩**：每修一条，都要能造出一个**会变红的最小夹具**。
> 只改代码而不留夹具，这条缺陷迟早以另一种形状回来——这个仓库里已经发生过两次（见缺陷 20 与 22 的"最小复现"栏）。

## 第一批：移植与自省期（1–17）

### 1. `local_graph` 无界循环（已修）

**症状**：提取在某个插件上永远跑不完，98% CPU 空转，队列无界膨胀。

**证据**：在 `@liustack/modlens` 上跑到 25 秒时打印 `iters=100000 queue=325012 seen=8` —— 循环了 10 万次，队列积压 32 万条，却只解析出 8 个文件。

**根因**：`seen` 同时承担了两个职责。依赖靠**补扩展名**才解析成功时，写入 `seen` 的是解析后的路径（`b.js`），而队列里传的是未解析形态（`b`）；于是 `rel in seen` 永远不成立 → 每次访问都重新展开它的导入 → 有环就无界膨胀。

**最小复现**：`tools/parity/fixtures/hang-cycle/` —— 3 个文件全部用无扩展名的 ESM 相对导入，其中 `a.js` 与 `b.js` 成环。

**修法**：把「检查过」（`visited`）与「解析成功」（`seen`）分开。desktop profile 从「10 分钟未完成」变为 **1 秒**完成，三个回归基准**逐字段不变**。

### 2. 副作用导入完全漏检（已修）

提取 import 的正则只认 `from '...'` / `require('...')` / `import('...')`，**`import './x'` 这种纯副作用导入不匹配** —— 而它是很常见的装配写法。后果：只靠副作用导入串起模块的插件会得到「0 个服务引用」，看起来干净，实际什么都没扫到。

### 3. 第三方 vendored 代码把 `ctx` 遮蔽掉（部分解决）

`dsh-better-sidebar` 打包了 `lib/client-mermaid.js`（12.5 万行，mermaid / chevrotain）。里面有：

```js
ctx.parser.consume(index, token, operatorAssignment)
```

这里的 `ctx` 是**解析器上下文**，与 Cordis 的 `ctx` 无关。提取器只看名字，把 `parser` 当成宿主服务，还凑出 **40 个方法**。同类：`ruleNames` 是个 `const ruleNames = new Set()` 局部变量，也被当成服务。

**现状**：不靠"看清语义"解决，而靠**三档确定性**兜住（从正则得到的调用点一律标「疑似」，不呈现得像确定的一样）。彻底解决需要真绑定分析（见缺陷 21 所在的那一批）。

### 4. 插件自定义服务被当成宿主服务（已修，A5）

`dsh-better-sidebar` 里有 `ctx.provide("betterSidebar", service)`。也就是说 `betterSidebar`、`betterLocale`、`pet`、`agentTeams` 这类是**插件自己提供的服务**，供其他插件消费。

若与宿主服务一视同仁，提供方不在场时消费方会被判成「依赖了不存在的服务」——**把「插件之间的依赖关系」误报成「与 DSH 版本不兼容」**。

### 5. 客户端种子是整包遍历（过宽 → 已改为来源分桶）

收集客户端代码时会把包里**所有路径含 `client` 的 js 文件**都拉进依赖图，包括 `lib/client-mermaid.js` 这种 vendored bundle。这既是缺陷 3 的入口，也是性能问题的来源。

**最终做法**：文件集合**不动**，给每个文件标来源桶（`host-entry` / `client-entry` / `client-extra` / `fallback`），写进 `provenance.json`；`client-extra` 的调用点标**疑似**。（为什么不动集合见下一条。）

### 6. 懒加载 chunk：**不是**死代码（已定，不按入口收窄）

这一条差点让我做错一次决定。

原计划是「客户端种子只取 `exports["./client"]`，缺席才回退路径遍历」，动机是排除 vendored bundle。**实测否决了它**。`dsh-better-sidebar` 把客户端代码切成多个 chunk，通过**自己宿主半边的 HTTP 路由**取回：

```js
/** Chunk script endpoint served by the plugin host half (src/bundle-route.ts). */
const CHUNK_URL = (name) => `/sidebar/bundle/${name}.js`;
```

于是 `lib/client-editor.js`（2.0 MB）、`client-locale.js`（732 KB）、`client-mermaid.js`（6.9 MB）都是**会真实运行的代码**，而从 `lib/client.js` 出发做静态可达性分析**永远够不到它们**（对 `client-mermaid` 的提及次数是 0；对另外两个各 1 次，还只出现在注释里）。

按原计划收窄 = 静默删掉真代码。**这个方向的错误（假阴性）比多扫（假阳性）严重得多。**

### 7. `.d.ts` 会被当成源码捞进来（已修）

`.d.ts` 以 `.ts` 结尾，会被「路径含 client 且扩展名是 `.ts`」的遍历命中，尽管它不含任何可运行代码。desktop profile 的客户端两桶共 846 个文件，其中 **342 个是 `.d.ts`**。

排除它**零风险**：客户端桶从 829 降到 487，而 `static.json` 输出**零变化**。

### 8–11. 一条不变式成批抓出来的四类（已修）

这四条不是设计时想到的，而是**一条不变式**在写出来的当天抓出来的：「每个调用点都必须能在它声称的 `file:line` 上被源码字节验证」。desktop profile 上 942 个调用点里有 **163 个（17%）对不上**。

| # | 缺陷 | 实测证据 |
|---|---|---|
| 8 | **裸名规则没有边界**：拿「名字在任何字符串里出现过」去匹配，命中同文件里毫不相干的局部变量 | 中间态调用点从 942 爆到 **7477**；`store`/`scale`/`root`/`tokens`/`consume` 全被当成服务 |
| 9 | **`ctx.get` 匹配式太紧**：`ctx.get("x", false)`（带第二参数）与 `ctx.get ("x")`（带空白）都匹配不到 | `dsh-pet` 的 `deepseekAccount` 依赖整条不可见 |
| 10 | **转手链只认一跳**：`const store = ctx.get("x")` 之后 `const store2 = store` 就断链 | 断链后 `store2.foo()` 找不到归属，而 `store.foo()` 被记到**另一个**服务头上 |
| 11 | **作用域注入的参数被忽略**：`ctx.inject(["a","b"], cb)` 的回调形参按**位置**绑定到服务 | 这是该生态最常见的写法之一，原实现一条都看不见 |

修法分别是：只对「插件自己声明过 / 官方双端目录里有」的名字用裸名规则；放宽 `ctx.get` 并识别第二参数；迭代收敛的绑定图（上限 4 跳）；按位置绑定回调形参。

### 12–17. 一次盲测探针交出来的六条（已修）

| # | 缺陷 | 实测证据 | 修法 |
|---|---|---|---|
| 12 | **CLI 空操作**：脚本路径带符号链接祖先时静默什么都不做 | macOS 上 `/tmp` → `/private/tmp`：`argv[1]` 是 realpath、`import.meta.url` 是给定路径，词法比较 false → exit 0、无输出、三个文件一个都不写 | 两边都取 realpath 再比 |
| 13 | **空白漏报**：服务名与点号之间有空白时调用整条漏掉 | `ctx.alpha .register(1)`、`ctx.beta\n.register(1)` 一个都没进 services | 统一加 `\s*` |
| 14 | **`fallback` 扫描依赖 `readdir` 顺序** | 把 `readdirSync` 反转后 fallback 包的 `callSites` 顺序会变 | `.sort()` |
| 15 | **`walkFiles` 看不见符号链接** | `Dirent` 对符号链接 `isFile` 与 `isDirectory` **都是 false**；而 pnpm 恰恰把包目录做成符号链接 | 用 `statSync` 补判定，断链跳过不抛 |
| 16 | **`const inject = [...]`（声明后引用）不被识别** | `dsh-mnemon-strategy-*` 一族被判成「0 个服务 → 可用」，而它们依赖的 `mnemonMemory` 当前 profile 里**无人提供** | 识别 `inject`/`injectDeps` 的数组字面量赋值 |
| 17 | **顶层 `callSites` 丢插件名** | 两个包都有 `lib/index.js` 时都是 `{file:"lib/index.js",line:1}` —— 按 file:line 定位会取到**错插件的源码** | 调用点新增 `plugin` 字段并进排序键 |

**第 16 条最值得警惕**：它不产生错误结论，它产生**沉默**。工具对一个真实缺口只字不提，用户却以为自己拿到了结论。假阳性让人多查一次，假阴性让人以为已经查过 —— 后者更贵。

**判据的自我修正**：第 16 条修好之后，我先给 `@fixture/pending`（声明了 `noSuchServiceAnywhere` 但从不调用它）写了判据「ok」，因为「代码没调用它」。它当场就红了 —— **代码没调用它不是理由，声明本身就是依赖**。判据改为 `broken`。这条记下来是因为它说明：判据写错时会被自己的 fixture 抓住。

### 边界与已知残留（第一批）

- `patchUnparsed`（patch 里读不到 `- name:` 就退回整包扫描）**曾被误当成第 16 条的修法**。实测它会命中 18/21 个真实插件（它们的 patch 都写成 `- insert: [- id: ...]`），把 host-entry 从 118 打到 10、fallback 打到 1359 个文件 —— 那不是修 bug，是把污染面放大一个数量级。已回退。
- 符号链接**包**仍然会被静默跳过（断链）—— 有意的（不抛），但未记账。
- 两个 `node_modules` 条目同名（pnpm 别名/重复 store 链接）时，`perPlugin` / `provenance` 以包名为键，**先出现的会被静默覆盖**。

## 第二批：一致性期（18–24）

这一批的共同点：它们**几乎都不是"少认了一处"，而是"把某个事实记错了地方"**。
也正因为这样，它们全都**通过了当时的全部测试**。

### 18. `provide` 的**数组声明**不被识别（已修）

**症状**：desktop profile 报 7 个 `dsh-mnemon-*`「依赖的服务由其它插件提供，当前 profile 里没有提供方」—— 而提供方 `dsh-mnemon` **就装在同一个 node_modules 里**。

**根因**：`provide` 与 `inject` 是**对偶**的，代码处理了 `inject` 的数组形态，`provide` 却只认 `ctx.provide("x")` 调用。而 `dsh-mnemon` 用的是：

```js
const provide = ["mnemonMemory"]
export { apply, inject, name, provide }
```

**修法**：也认**导出的**数组声明（要求"导出"，因为只有导出的才是插件契约，与 `export { inject }` 对称）。

**效果**：可用 3 → **9**；真实回归基准 `parityfix` 快照**零改动**。

**最小复现**：`test/fixtures/micro/node_modules/@fixture/` 下的 `provideexported` + `consumerofexported`（必须 ok）与 `providerinternal` + `consumerofinternal`（必须 broken）。**成对存在**：一条拦假阳性，一条拦"修假阳性时把正则放松过头"。

### 19. 正则**读注释与字符串**（已修，但**中间「假修」过一次**）


> ⚠️ **这一条值得单独记一次失败**：第一版只把**声明规则**改到掩码文本上，
> 而**调用点三条规则仍然读原文**，却在本文档里写成了「✅ 已修」。
> 也就是说**文档说修好了，代码没有** —— 它会一直骗到下一次有人写夹具踩中为止。
> 而这次正是被一个新夹具的**注释**踩中的（注释里写了示例，提取器当真）。
>
> 教训两条，都是流程性的：
> 1. **「已修」必须有夹具兜着**。没有夹具的「已修」只是「我改过一处」。
> 2. 中途用 `git checkout lib/extract.mjs` 回滚过一次纠缠的改动，那次回滚
>    **悄悄带走了这个修复**，而测试全绿、我没发现。
>    **大范围回滚之后必须重跑「这次要验的东西」，不能只看测试绿。**


**症状**：写在注释里的示例代码会被当成真的调用。

**怎么发现的**：给夹具写负向对照时，注释里为说明"我故意**不**调用 `ctx.provide('internalOnlyService', ...)`"，把那个调用原样写了出来 —— 提取器把它当真了，**负向对照当场失效**。我用来自证的钉子，被我自己的一行注释拔掉了。

**真实影响**：`dsh-better-sidebar` 有两个文件在注释里写了 `ctx.provide(...)`。后果分两个方向：注释里的 `ctx.get("x")` 造出**假阴性**（不存在的依赖被当成声明过）；注释里的 `ctx.provide("x")` 造出**假阳性**（没人提供的服务看起来有人提供）。

**修法**：`maskCommentsAndStrings()` 把注释与字符串内容抹成空格，**逐字节等长、换行不动** —— 不能删，因为 `file:line` 靠字符偏移换算，删注释会让"注释里写不写示例"去改变真实调用的行号。

#### ⚠️ 这里的关键设计：两种掩码不能混用

| 用途 | 掩码 | 为什么 |
|---|---|---|
| **声明**解析（`inject = ["svc"]`） | 只抹注释、**保留字符串** | 抹了字符串就等于把这些声明全删了 |
| **调用点**扫描 | 注释与字符串**都抹** | 这里的误读直接造假阳性／假阴性 |

我第一版两处都用错了，**两个方向各翻车一次**：用抹过字符串的文本去解析数组 → `provide` 一个都认不出来、假阳性全部复活；用保留字符串的文本去扫调用点 → 没起到该起的作用。**这个分工是实测出来的，不是设计出来的。**

### 20. `unguardedPairs` 没去重就下结论（已修）

**症状**：作者的兜底**永远不生效** —— `guardedPairs` 里有它，`unguardedPairs` 里也有它，判定层于是照报。

**根因**：同一个 `svc.method` 常被**多条规则在同一行各收一次**（`ctx.settings.register('x')` 会被 "ctx-member" 档和裸名档同时收下），而两档的 `guarded` 判定不一定一致。在 `addCall()` 里直接累积 `unguardedPairs`，等于**用"输掉去重的那一条"污染结果**。

**修法**：两个集合都从**去重后的站点**派生，用同一个口径。

**怎么发现的**：靠夹具里 `settings.register` **同时出现在两个集合**里 —— 那是个自相矛盾的状态。

### 21. 兜底识别漏掉 `?.()` 形态（已修）

**症状**：`dsh-better-sidebar` 的 `ctx.sessions.binding?.(newId)` 被判「宿主方法缺失」，而作者明明写了兜底。

**三个 bug 叠在一起，只修一个会更糟**：

1. **调用点正则要求 `method(`**，所以 `method?.(` 这种调用**整条不被收下** —— 假阴性，表现为"这个插件没有依赖、一切正常"。
2. 修了 1 之后，如果兜底识别还**只看匹配前面**，立刻变成假阳性（`?.` 在方法名**之后**）。
3. 旧 `guardRegex` 还把 `typeof x.m === "function"` 里的 `?.` 写成**必选**，于是最普通的写法反而认不出来。

**修法**：三种形态全认 —— ① `svc?.method`、② `svc.method?.(`、③ `typeof svc.method === "function"`；`isGuardedNear` 的窗口改成"前 400 / 后 80"字符。

> **形态清单是去真实插件里 grep 出来的，不是凭印象写的** —— 上一版就是凭印象，所以漏掉了最常见的那种。

### 22. `localBindings` 按变量名聚合、后写覆盖先写（已修）

**症状**：不变式 ⑤（「别名调用点必须能被 `localBindings` 解释」）在 desktop profile 上报红：

```
dsh-better-sidebar lib/index.js:4956: via=alias matched=session 归属 sessions，但绑定表里对不上（没有该变量）
```

**根因**：`session` 这个变量**在不同文件里绑到不同的东西** —— `lib/client-registry.js` 里同时承载 `remote` 与 `sessions`（歧义），`lib/index.js` 里是干净的一个。而 `localBindings` 是 `Map<变量名, 一条记录>`、**后写覆盖先写**，于是别处那条有效绑定被歧义那条盖掉了。

**修法**：新增**文件维度**的视图 `bindingsByFile: Map<"变量名|文件", Set<服务>>`，每次出现都记、不覆盖；`bindings` 由它派生（每条带 `file`）。

**消歧策略不变**（同名变量绑到多个服务就整体弃权），只是不再让一个文件里的事实**覆盖**另一个文件里的。

> **没有放宽不变式** —— 它抓到的是真的对不上账。
> 这条已经在仓库存活了一段时间，而每次"跑测试"都因为它在一个机器相关的子集里而被略过。

### 23. `logger` 被当成宿主服务（已修）

**症状**：`dsh-keep-awake` / `dsh-pet` 都写 `inject: ['logger']`，若把 `logger` 当成服务，就会报「宿主服务缺失 → 插件会停在 pending」。

**实测**（用 `--probe-boot` 起了一次真实宿主，把 `logger` 放进探针名单）：结果 `present: false`，而同一批里 `tools` 39 个方法、`agents` 24 个都在。

**结论**：`ctx.logger` 与 `ctx.loader` / `ctx.effect` 同类，是 **Cordis 的上下文便利成员，不是可注入的服务**。已加进 `CORDIS_CONTEXT_BUILTINS`。

> 这条是"**先猜后验**"的反面教材：直觉上 `logger` 太像服务了。**能实测的事就不要推断。**

### 24. 客户端半边被拿宿主面判（已修）

**根因**：`sessions` 这类服务**两端都有**（宿主实测 14 个方法，浏览器侧另有一套）。于是命令行拿宿主面去判浏览器侧的调用，必然对不上。三类假阳性全都出现过：

| 假阳性 | 为什么 | 修法 |
|---|---|---|
| `modules` / `settingsScope` / `configForms` / `remote` 报「宿主服务缺失」 | 服务只在浏览器侧，宿主探针必然看不到 | 判据 c：插件自己的 `dsh.client.inject` 点了名；判据 d：在插件的**客户端文件**里被用到而宿主没有 |
| `sessions.scope` / `emit` / `subscribe`（写在 `lib/client.js`）报「宿主方法缺失」 | 命令行的宿主面**看不见客户端那套方法** | 方法级判定**只看宿主侧调用点**；只在客户端调用的方法归「客户端半边，需界面验证」 |

**效果**：`不兼容 4 → 0`，`可用 9 → 14`（`--probe-boot` 实测）。

> 判据 b（"出现的文件**全部**在客户端桶里"）在**共用代码**面前必然失效：同一个 `lib/index.js` 既跑在宿主也被浏览器 import，于是服务总会留下一个宿主文件。所以才有 c 与 d 两条补丁。

### 25. `ctx.inject` 的**单参数**回调没被认成上下文对象（已修）

`contextObjectNames()` 早先要求回调**至少两个形参**，并把**第二个**当上下文 ——
理由是「第一个是被注入的服务」。**实测这个前提在真实插件上几乎不成立**：

| `ctx.inject(cb)` 的形参个数 | 实测次数（desktop profile） |
|---|---|
| 0 个 | 1 |
| **1 个** | **27** |
| 2 个 | **0** |

于是 **27 处全部被漏掉**，而它们都是 `<head>.<svc>.<method>()` 这种最常见的写法：

```js
ctx.inject(["tools"], (toolsCtx) => {
  toolsCtx.effect(function* () {
    yield toolsCtx.tools.register(createRenderUiTool());   // ← 原来是看不见的
  });
});
```

**修法**：单参数时那个参数就是上下文对象；多参数时保留原来的「取第二个」约定。
安全性：它只让**两个点**的形态变得可判（要求作者确实写了「上下文对象的成员再取服务」）；
若作者把参数直接当服务用（`(tools) => tools.register(...)`，一个点），这条不介入 ——
那条通路归 `injectParamBindings` 按位置管。

### 26. `this.ctx.<svc>.<m>()` 被 lookbehind 挡住（已修）

主规则 `ctx.<svc>.<method>()` 带 `(?<![\w$.])` —— 挡住 `myctx.` 是对的，
但它**顺带也挡住了 `this.ctx.`**（`ctx` 前面是 `.`）。而 class 式插件到处写 `this.ctx.xxx`。

**实测 desktop profile：这个形态出现 32 次、涉及 4 个服务**
（`agents` / `logger` / `sessionPersistence` / `storageDomain`），全部不可见。
其中 `dsh-mnemon` 的 `this.ctx.agents.get(...)` 让它被判成「`agents` 没有任何调用点」
—— **把一个真调用报成了「没用到」**。

**修法**：**加一个精确的名字**（`this.ctx`），而不是放宽 lookbehind。
放宽成 `(?<![\w$])` 会让 `foo.ctx.<svc>.<m>()` 也命中，而那个 `ctx` 可能是别人的上下文
（React context、请求上下文……）。要支持别的写法时，同样**先去真实插件里量出现次数**。

### 27. 「服务名出现在哪些文件」误用**抹掉字符串**的文本（已修）

修缺陷 19 时把 `perFile` 存的文本改成「抹掉注释与字符串」的 `code`，
而**同一份文本要回答两个不同的问题**：

| 问题 | 该用哪份文本 | 为什么 |
|---|---|---|
| 这个文件里有 `svc.method(` 这种**代码**吗？ | 抹掉注释**与字符串** | 字符串里的同名文字不是调用 |
| 这个服务名在哪些文件里**被提到过**？ | 只抹注释、**保留字符串** | `ctx.get("remote.commands")` 的名字就在**字符串**里 |

混用之后一批服务「哪儿都没出现过」，于是**从「客户端半边」掉进「宿主服务缺失 → 致命」**。
实测把 `dsh-pet` 从**可用**打成了**不兼容** —— 三个回归基准当场变红，是测试拦住的一次自伤。

**修法**：`perFile` 同时留两份（`text` 给调用点扫描、`mention` 给「出现在哪些文件」），
两份都等长，行号不受影响。

### 28. 上下文对象的**别名**没被跟踪（已修）

`ctx.inject(["settings"], (scopedCtx) => { const scoped = scopedCtx; ... })` ——
上下文对象被转了一手，于是 `scoped.settings.register(...)` 一条都看不见。

**实测规模很小但是真的**：desktop profile 上 27 个上下文对象里有 **3 个**这样转了手
（`dshmarket` 的 `const scoped = scopedCtx` 与 `const host = hostCtx`）。

**修法**：认「整句就是赋值」的形式（`const|let|var X = <已认出的上下文>`），
**迭代到不动点**（上限 4 轮，与别处的绑定追踪同一个上限 —— 上限是防**别名成环**，不是怕慢）。

> 这里"窄"比"全"要紧：多认一个假名字，会让该名字下**所有** `<name>.<svc>.<m>()`
> 都变成"真调用"，也就是**把假阴性换成假阳性**。所以只认这一种写法。

#### 剩下的那一类：**跨函数追踪**（不做，理由如下）

修完 28 之后，同一口径下只剩 **1 处**（desktop profile）：

```js
// dshmarket/lib/routes.js
function register(host) {           // ← host 是**参数**
  return host.webServer.register(route);
}
```

`host` 不是文件里的 `const X = <ctx>`，它是**从别处传进来的**。
要认它必须做**过程间分析**（调用图 + 参数传播）—— 那是"真解析器"的量级，
不是再加一条正则能解决的。

**所以停在这里**，并把边界写清楚：增量修法能吃掉"同一个函数体内的转手"，
吃不掉"跨函数传进来的上下文"。后者要的是真正的绑定分析（AST + 作用域 + 调用图）。

## 反复出现的那几类错误（比单条缺陷更值得记）

回顾这 24 条，真正反复的不是某个正则写错，而是四种**思维习惯**：

| 类型 | 实例 | 共同的形状 |
|---|---|---|
| **"没看到"与"不存在"当作同一件事** | 缺陷 3（`ctx` 被遮蔽）、缺陷 16（`inject` 数组）、缺陷 21（`method?.(` 不收）、缺陷 24（宿主看不到客户端服务）、缺陷 25（单参数 inject）、缺陷 26（`this.ctx`） | 输出**看起来干净**，而干净与"什么都没扫到"在报告里长得一样。**假阴性比假阳性贵。** |
| **凭印象写规则，而不是按代码实际长什么样** | 缺陷 21 的形态清单、缺陷 9 的 `ctx.get` 形态、缺陷 6 的"懒加载是死代码" | 都是"我以为它是这么写的"。修法是**先去真实插件里 grep 出形态分布**，再写规则。 |
| **把某个事实记错了地方** | 缺陷 19（读注释）、缺陷 20（没去重就下结论）、缺陷 22（按变量名聚合、后写覆盖先写）、缺陷 27（同一份文本回答两个问题） | 数据本身没错，**键取错了**。这类最难发现，因为它们**通过了当时的全部测试**。 |
| **靠 catch 兜住失败** | `w()` 的 `try/catch` 曾把探针的 `ENOENT` 咽掉，让探针**一声不响地不产出任何报告** | "尽力而为"的 catch 不是安全网，**它只是把失败藏起来**。 |

于是有两条规矩，它们不是风格问题：

1. **能实测的事不要推断。** `logger`（缺陷 23）与"懒加载是不是死代码"（缺陷 6）都差点被直觉带错。
2. **每修一条都要留一个会变红的夹具**，而且**两两成对**：一条拦假阳性，一条拦"修假阳性时制造假阴性"。
   `provideexported` / `providerinternal` 就是这对（缺陷 18）。

## 探针的两条边界（写给改 `probe/index.mjs` 的人）

这一节不讲故事，只讲规则。它们是有代价换来的。

**① 只记录结构，绝不记录内容。**

探针是一个**只读的形状探测器**，不是快照工具。它输出 `{ 服务名: { present, methods } }` —— 只有方法名，没有任何属性值。

为什么值得写成规则：一个跑在宿主进程里、要读遍所有服务的东西，它的默认动作很容易变成"把看到的值抄下来留作现场"。而服务里装着**凭据、令牌、用户数据**。更关键的是，**这个动作会持续复发**：不是手滑一次，是每跑一次就重新生成一份，并且完全不会让任何测试变红 —— 直到有人恰好去 grep 它。

要排查现场请用 `--keep` 看启动日志，不要去扩大探针的输出面。

**② 判据要卡在"值"，不要卡在"名字"。**

守卫测试（`test/secrets.test.mjs`）扫描仓库里的凭据形态。校准它的第一版把文档里**描述**凭据形态的写法也报成泄漏 —— 而那些写法是正确的。**一个爱乱报警的守卫最后一定会被忽略**，那它就不再是守卫。

所以每条判据都要求"看起来是真的值"（足够的长度与字符集），并且两个方向都要验：

- 拿真实样本喂进去**必须命中**（否则是空守卫）
- 拿占位写法喂进去**必须不命中**（否则是噪音源）

**③ 输出目录必须自己建。**

`w()` 的 `try/catch` 会把 `ENOENT` 咽掉，于是"目录不存在"的表现是**探针什么都不产出、也不报错**。所以进目录前先 `mkdirSync(recursive)`，并尊重 `DSC_OUT_DIR`。

**④ 只问 `services.json` 里点名的服务 —— 所以那份名单必须完整。**

探针不问的服务，在报告里与"不存在"**长得一模一样**（缺陷 23 的 `logger` 就是这么暴露的）。所以 `--probe-boot` 的流程是**先提取、再拿面**：把本次涉及的**全部**服务名交给探针。
