# API 目录候选审查与验收

API 目录记录某个 DSH 制品内生成的服务和方法声明。目录不是运行时 API 面：抽象服务的空方法数组不证明运行时没有方法；新增名称也不证明插件能够激活或业务能够完成。普通体检必须分别展示实际 DSH 版本、参考目录身份和认证范围；未来版本不能借用参考目录的已验收状态。升级预检继续只接受明确支持的精确版本。

下面的流程把来源核验、规则复核和集成验收作为三个独立步骤。离线工具只完成第一个步骤并生成差分，退出 0 不代表兼容认证。

## 1. 封存对应制品，显式提取候选

取得目标版本的官方 DSH 安装包或已有本地安装，记录下载页面/渠道、包名、精确版本、取得日期、平台与架构、安装包 SHA-256、实际 `app.asar` 路径和 SHA-256。包来自何处以及其官方真实性需要审查者确认；本工具核验的是所给本地归档与候选目录的一致性，不能认证分发者身份。不要从正在更新的安装目录提取；先保存稳定的本地副本。

在仓库根目录执行以下命令。示例版本 `0.3.0-rc.1` 仅演示候选流程，**不表示受支持**。使用新建的私有目录和显式输出路径，避免覆盖任何已验收目录。Python 只读取归档中的生成代码文本，不加载这些 JavaScript，也不执行插件。

```sh
review_dir="$(mktemp -d "${TMPDIR:-/tmp}/dsh-catalog-candidate.XXXXXX")"
asar='/绝对路径/目标版本的/app.asar'
candidate="$review_dir/dsh-api-catalog-0.3.0-rc.1.candidate.json"
shasum -a 256 "$asar" > "$review_dir/app-asar.sha256"
python3 -I tools/catalog/extract-host-api.py "$asar" "$candidate"
```

同时保存安装包本身的摘要及取得记录。候选必须包含 `_dshVersion`、两端 `_source` 路径、对应原始文件字节的 `_sourceSha256` 和 host/client 方法清单；缺失元数据的历史目录可以作为差分基准，不能直接作为新候选。提取器的最低服务数量检查失效时应停止，研究生成器格式变化并为解析修复补测试，不能删除检查以得到成功结果。

## 2. 离线核验来源并审查 API 差分

`--before` 选择最近一次已验收的相关参考目录。它是差分基准，工具不会替它重做历史来源认证。候选只有与 `--asar` 内重新提取的版本、固定源文件路径、原始源文件 SHA-256 和两端 API 内容全部一致，才返回 `sourceVerified:true`。

```sh
node tools/catalog-review.mjs \
  --before rules/dsh-api-catalog-0.2.1-rc.2.json \
  --candidate "$candidate" \
  --asar "$asar" \
  --json > "$review_dir/catalog-review.json"
```

JSON 包含前后目录的文件 SHA-256、候选版本和来源身份；`diff.host` 与 `diff.client` 分别列出 `servicesAdded`、`servicesRemoved`、`methodsAdded`、`methodsRemoved`。方法项为 `{service,method}`，包括整个服务新增/删除所带来的方法。排序稳定，不以 JSON 键或方法数组顺序制造差分。去掉 `--json` 可查看文本输出。

退出码约定：

- `0`：候选来源与内容核验成功，差分可供审查；`semanticReview` 和 `integrationAcceptance` 仍为 `pending`，`certification` 为 `not-granted`。
- `3`：参数、文件形状、版本、来源、内容或资源检查失败，或者 Python 缺失、超时、提取失败；JSON 中 `sourceVerified:false`。不得把不完整结果当作无差分或验收通过。

工具不联网，不执行被测插件，不改输入、默认目录、规则、pin 注册表或支持版本。每个 JSON 最多 2 MiB；ASAR 最多 4 GiB、头最多 8 MiB、三个选定源条目各最多 8 MiB。拒绝链接、FIFO、非普通文件、非 packed 条目和越界条目。复用仓库 Python 提取器，使用隔离模式及显式私有临时输出；子进程预算 10 秒，超时强制回收，输出缓冲最多 1 MiB，成功与失败均清理自有临时目录。路径检查与前后文件身份观察不承诺操作系统原子快照、防协同篡改签名、全进程 RSS 或硬实时上限；审查时应使用稳定本地制品。

## 3. 人工复核规则语义

逐项解释新增/删除及未变名称背后的签名、生命周期、权限、分端和注入前提变化，关联官方源代码或文档证据。核对 `rules/` 中规则的适用版本、运行时面优先级、`ruleRef`、影响依据及弃权条件，保留每项的审查结论。目录相同也可能存在行为变化，不能以空差分省略这一环节。

不要因为目录新增/删除就调整 severity，不要把 host 证据套给 client，也不要把某个 profile 的运行时证据套给另一个版本或 profile。需要改规则时，先提供能复现语义差异的针对性测试及依据，再单独 review 规则变更；不能用放宽规则掩盖未观测状态或验收失败。

## 4. 针对性回归与真实 DSH / Chrome 验收

先运行 `npm test` 和相关规则/目录/普通报告/升级预检测试。针对实际 API 变化补充正反例，检查报告的实际 DSH 与参考目录版本/摘要、未知版本提示及精确升级门禁；新候选的来源工具绿色不能替代这些行为检查。

在目标平台上使用对应版本的真实 DSH、独立私有 profile 和 Chrome 完成已授权的集成验收，封存确切插件制品、目录/规则摘要、DSH/Node/Chrome 版本及日期。覆盖插件激活、host/client 调用、关键 HTTP/DOM 业务、故障与恢复、普通报告及升级预检的身份与隔离。静态发现、服务观测、受控故障和自然业务真值分别记录，保存日志、截图、退出码及资源清理证据；无法测到的内容明确列为未验收，不沿用旧版本的测量结论。

## 5. 经 review 后手动接受，保留回退

人工语义复核和目标环境验收均完成后，提交可审查的变更：新增版本独立目录、更新目录 pin 注册表（当前为 `lib/contracts.mjs` 的 `CATALOG_REFERENCES`）、选择策略以及适用的支持版本列表（升级预检为 `lib/upgrade-contract.mjs` 的 `SUPPORTED_PREVIEW_VERSIONS`），同步契约副本和说明。记录候选文件 SHA-256、源文件摘要、审查人与日期、针对性测试与真实验收证据以及明确的认证范围。pin 与支持列表的变更需要 code review，工具的退出码不构成这一授权。

保留旧目录及旧版本行为；失败或证据不充分时，候选留在证据目录、保持未认证，不加入 pins 或支持版本。若已接受后需回退，应恢复原 pins/支持范围并重新验证普通报告提示和升级预检拒绝行为，保存失败原因及后续处置。不要覆盖旧目录来隐藏回退，也不要把未通过的未来版本标成已兼容。

最终将候选、来源记录、差分、语义复核和验收证据从临时目录复制到稳定的审查存档，再清理自有临时目录。共享前检查绝对路径、包名和日志中可能包含的私人信息。
